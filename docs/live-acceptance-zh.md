# 真机验收

> Owner: @FrozenYty · Revisit when: 对新 Host 构建跑过一次清单、某项检查多出前置条件，或某项检查被退役

**本仓库里唯一能证明 Host 服务行为的东西，就是这份清单。** 其他检查证明的都更窄：`scripts/check.mjs` 证明 bundle 自洽，`scripts/schema-check.mjs` 证明 Host 的校验器接受我们的**形状**，测试套件在夹具上证明我们的**逻辑**。它们都不会发现 `agentTeams.listMembers()` 或 `tokenMeter.contextPressure()` 换了返回形状——而那种改动会让本插件坏掉、同时所有自动检查全绿。

所以这份流程在**每次 Harness 升级之后**执行，且只有真实调用能抓到这一类断裂。结果连同**所针对的 Host 版本**记入 `PROGRESS.md`：本文是流程，`PROGRESS.md` 是记录，而 `PLAN.md` 只有在它需要被排期而不是被顺手执行时才挣到一条任务。

**它证明不了什么：** 它只是**某一个 Host 构建**的快照。通过只说明当天 Host 的表现符合预期，对下一个构建什么也没说；它也不能替代套件——真机通过而夹具测试失败，说明这一轮真机量错了东西。

**把数字读成关系，不要读成字面值。** 下面的每个计数都属于某个 profile 的某一天；换一个 profile 计数就不同，必须成立的是它们之间的关系，所以每项检查写的是关系而不是数值。

## 1. 归档读取有上限，并且自己说出来

**怎么调** 带 `archived: true` 调 `list_members`。
**正确是什么样** `archived_returned` 等于上限（今天是 50），且在确实有更多记录时**小于** `archived_total`——也就是回答同时说明它展示了多少、以及它持有多少。2026-11-13 实测：`archived_returned: 50`、`archived_total: 74`；**2026-11-14 实测：`archived_returned: 50`、`archived_total: 75`**。
**不符时最可能意味着** `archived_returned` 大于 50：上限没有生效，而无界读取正是这个上限要防的事。文件明明有更多、`archived_total` 却等于 `archived_returned`：总数是在返回的切片上算的，调用方从此看不出还有历史被藏起来。

## 2. 普通读取从不打开归档——用算术来验

**怎么调** 不带标志调 `list_members`。
**正确是什么样** 报出 `archived_records`、不出现 `archived` 行，而且**算术闭合**：`retiredChildIds` 的长度减去仍留在花名册里的墓碑数，等于 `archived_records`。2026-11-13 实测：**95 − 21 = 74**。**2026-11-14 复跑：97 − 22 = 75**，正是归档的行数；先前那次也算得通（96 − 21 = 75），所以两次都在这里。这个减法就是不用调试器也能确认热路径被尊重的方法：如果热路径真的读了那个文件，计数就可能来自错误的地方，差值不会闭合。
**不符时最可能意味着** 算术不闭合：计数与文件互相矛盾，要么归档在该被读的时候被读了，要么窗口冲刷了却没有写入。不带标志却出现 `archived` 行：这个标志已经不再意味着任何东西。

## 3. 恢复一条已归档的墓碑会按名拒绝

**怎么调** 对一个已知已归档的目标调 `restore_member`。
**正确是什么样** `reason: "archived"`，消息**点名归档文件与归档时间**，且**什么都没有改变**——没有回收站条目、没有记录移动，之后的花名册与之前完全一致。2026-11-13 实测：拒绝点名了文件与归档时间，且没有移动任何东西。
**不符时最可能意味着** 只回了一个笼统的"找不到"：带类型的拒绝丢了，人再也分不清"从未存在"与"已离开花名册"。有任何东西被移动：在拒绝时仍然写入，正是本插件被修过不止一次的假成功缺陷。

## 4. 一次真机退役把产物写进工作区回收站，并留下可携带的来源

**怎么调** 对一个产物存在的成员调 `retire_member`。**2026-11-14 复核**：一次新的退役写出了 `originalRelPath`、产物进入工作区回收站、`trashState: done`、没有 `originalPath`。
**正确是什么样** 产物落在**工作区**的回收站里（`<工作区>/.agents/team/trash/…`，绝不是 `~/.dsh/team-roster`）；`originalRelPath` 以 `<slug>/<leaf>` 写出且**用正斜杠**；记录上**既没有 `originalPath` 也没有 `trashPath`**（ADR 0034）。2026-11-13 实测：正是如此——产物在工作区下、相对来源用正斜杠、两个绝对字段都不存在。
**不符时最可能意味着** 产物出现在 `~/.dsh/team-roster` 下：冻结目录被当成了写入目标，而它只该作为遗留读取腿。新记录上出现 `originalPath` 或 `trashPath`：某个版本又回去写绝对路径了，花名册重新变得不可携带。

## 5. 一条没有绝对路径的记录也能恢复成功

**前置条件，且不可省略：** 该成员必须是在 **v0.34.0 或之后**退役的，这样它的记录才带 `originalRelPath` 且没有绝对路径。
**怎么调** 对它调 `restore_member`。
**正确是什么样** 会话根从**持久化服务仍能报告的兄弟会话**推导出来，slug 取自记录，产物被移回原路径——记录回到 `active`，回收站条目消失。2026-11-13 实测：正是按这些条件成功。**这是整份清单里最强的一项**：它证明相对来源能在真实存储上解析，而任何夹具都做不到。
**不符时最可能意味着** 回 `unresolved-root` 或笼统失败：兄弟腿没能找到根，那么先查会话根的推导，而不是记录。被移到不存在的路径：slug 接到了错误的根上。

## 6. 上限会真跑，而一次剪除可能在同一写入里让墓碑可归档

**怎么调** 执行一次让回收站越过生效上限的退役。
**正确是什么样** 一个产物被剪除（退役结果里的 `pruned` 大于零），**并且**因此有一条更旧的墓碑变得可归档——同一次写入把它移进归档，于是文件多一行、花名册少一条墓碑。2026-11-13 实测：剪除 1 个，**74 → 75** 行，新可归档的墓碑在同一次写入里被冲走。
**触发条件，v0.40.0 之后：这已不再是普通运行会遇到的事。** 默认上限现在是 200，没配置过 `trashLimit` 的 profile 根本到不了上限、也就从不剪除。要跑这项检查，请用一个回收站已到上限的 profile，或显式设置一个足够小的 `trashLimit` 使其生效。行为仍然真实——只是触发点挪了；而一项没人能碰巧满足的检查，必须把触发条件写下来。
**这种涌现行为是预期内的，不是错误。** 它是两条规则相遇：上限删掉产物（ADR 0011/0012），窗口随后允许该记录离开，因为它的字节已经不在（ADR 0030）。不知道这件事的读者会把一次正确的运行读成缺陷。
**不符时最可能意味着** 产物被剪除而记录仍留在花名册上：那次写入没有应用窗口，说明这条约束在某处被忘了。归档增长却没有剪除：某条记录因上限之外的理由离开了，而四个条件本该拒绝它。

## 7. 宿主钩子自报状态，存储块点名文件

**怎么调** 调 `list_members`（带不带标志都可以）。
**正确是什么样** `host_hooks.panel_filter`、`roster_filter` 与 `slot_credit` 都为 `installed`，`stripped_ids` 等于过滤器正在摘除的已退役子会话 id 数（2026-11-13 实测：95；**2026-11-14 复核：97**），并且 `storage.source: "file"` 且带工作区 `path`——不是 `storage-domain`，schema 已不再发布那个值（ADR 0031/0033）。
**不符时最可能意味着** 某个钩子 `absent`：插件加载时那项服务还不存在，官方面板或 `list_agents` 会显示本该被隐藏的成员。已有退役成员而 `stripped_ids` 为 0：过滤器装上了却什么也没读到——这比 `absent` 更糟，因为它看起来是健康的。`storage.source: "none"`：该 Lead 从未被绑定，在真实 profile 上就意味着根没解析出来。

## 8. 同一数据根下的两个 Lead 只看得到各自的归档记录

**状态：尚未运行——唯一仍未跑的检查。** 归档是每个数据根一个文件，而读取者必须只回答一个 Lead（ADR 0035）。今天这个 profile 只有一个 Lead 会话，所以这条规则只有套件覆盖、没有任何真机观测。
**前置条件：** 两个 Lead 会话共用一个数据根，且各自至少有一条已归档墓碑。
**正确是什么样** 每个 Lead 带标志的读取只返回自己的记录，`archived_total` 对应那个 Lead 的行数，而不是整个文件的行数。
**不符时最可能意味着** 一个 Lead 的记录出现在另一个人的回答里：读取者是按文件回答而不是按 Lead 回答，那么一旦存在第二个 Lead，第 1、2 项里的每个计数都失去意义。

## 9. 一条归档记录按身份被找到，且位于上限之外

**状态：2026-11-14 已跑，两个方向都跑了。** 对 `impl-lifetime` 的命中——它是 75 条归档记录里最旧的一条，因此位于最新 50 条之外——恰好返回一行，`archived_returned: 1` 且 `archived_scanned: 75`；对 `nobody-g3` 的未命中返回 `archived_returned: 0`、`archived_scanned: 75`，以及点名该目标的消息。
**前置条件，而且它就是这项检查的意义：** 归档里必须有**超过上限的记录数**，且目标**只存在于上限之外**。在短归档上测过的查找，会在功能已经消失时依然通过——所以文件的大小是检查的一部分，而不是背景信息。
**怎么调** 带 `archived: true` 调 `list_members`，并把 `archived_target` 设为一个比最新 50 条更旧的目标（或它的原始 member id）。
**正确是什么样** 命中时**恰好返回一行**、`archived_returned: 1`、该行带 `archived` 与它的 `archived_at`，`archived_scanned` 报出它读了多少行——扫描数大于 50 正是它看过窗口之外的证据。未命中时返回 `archived_returned: 0`，**并且**带 `archived_scanned`、`archived_total`，以及点名该目标的消息，绝不是一次空的成功。
**不符时最可能意味着** 对一条你确知在文件里的记录返回零：要么你传的目标不是那条记录的身份（按设计，部分名字不算匹配），要么扫描被 50 截住了——后者正是这项检查存在的理由。未命中时 `archived_scanned` 缺失、或等于返回条数：回答没有报告它的代价，于是"未命中"与"读取失败"再也分不开。在 `"Replaced by reviewer-g2"` 这类文字上命中：文本匹配回来了，身份不再是身份。
## 10. 每个成员都报出它已花费多少，来自三个来源之一

**状态：2026-11-14 已跑，三个来源都验到了。** 一个驻留成员在它的第一次已提交请求之前回答 `spend_tokens: 0`——这是一次测量，不是省略；五个 standing 角色全部未加载，每一个都给出了数字；而本次运行中退役的某个成员，其墓碑上带着 `spendTokens: 63897`，在产物离开会话根进入回收站之后，它那一行仍然报出这个数。
**前置条件，而且它就是这项检查的意义：** 三种成员各一个——**驻留**且背后有已提交请求的、**未加载但未退役**的、以及**在 v0.39.0 或之后退役**的。退役这一种带版本下限：v0.39.0 之前写下的墓碑没有数字、也永远不会有，所以那里缺字段是正确答案而不是失败。若一个 profile 的退役全都早于该版本，这份清单根本跑不到第三个来源。
**怎么调** 不带任何标志调一次 `list_members`。
**正确是什么样** 三行都带 `spend_tokens`：驻留成员那一行读自它自己的投影；**未加载**成员那一行读自 Host 的缓存——这正是本项检查存在的理由，因为它从前是缺的；**已退役**成员那一行是**退役时冻结**的值，之后每次读取都一样、永不再增长。活着的或未加载的行，数字可以增长、也可以在两次读取之间下降：一次重试增加一次尝试，而被最终样本替换掉的流式样本会减掉。当数字根本算不出来时——包括某次退役的折叠没有产出——字段被**省略**，绝不是 `0`。
**不符时最可能意味着** 未加载的行上的数字忽略了它上次加载之后的一切尝试：缓存返回了陈旧条目，先确认那段时间是否真的安静。墓碑**确实**来自本版本或更晚、却看不到数字：退役时的捕获没有发生，而那个值已不可恢复——这是这里唯一没有第二次机会的失败。已退役行的数字在两次读取之间**变了**：字段在被从活的来源重算，而不是从墓碑回答。在测不到的地方出现 `0`：字段被当成替身，而这是它绝不能做的事。既未驻留也未退役的行上的数字，在工作明显在花费时纹丝不动：列表那一腿没匹配上 header，应检查身份凭证。
