# 工作板

> Owner: @FrozenYty · Revisit when: 任务行、工作板动作或交接规则发生变化时

本插件自有的工作板：Lead 花名册记录上的那些行、适用于它们的上限与加载规则、两次调用重叠时一次工作板写入保证什么，以及决定成员未完成工作在替换、退役与恢复时如何变化的矩阵。这些行所在的记录见 `docs/roster-storage-zh.md` §1；点名它们的交接书见 `docs/handoff-zh.md` §1。相关决策：ADR 0017、ADR 0020、ADR 0022。

## 1. 工作板：行、上限，以及加载时拒绝什么

`tasks` 采用与已存模板相同的分工（`docs/handoff-zh.md` §3），并且更进一步。它的**结构**在加载时校验——必须是数组，每行必须是
对象，`id` 是非空字符串，`status` 是已知值，`owner` 出现时必须是非空字符串，且 id 不得重复——因为一条
无法表示任务的记录，也就无法为它作答。它的**内容**不校验：只是一个标题或正文太长、或者在写入上限出现之前就
已经超出列表上限，都照常加载，并由读取形式报告（行上的 `problem`，`docs/architecture-zh.md` §5），而不是拒绝整个域。这就是
`handoffTemplate` 先例用在最要紧的地方：否则某个 Lead 的一条陈旧任务，会把这台机器上所有花名册都藏起来，
包括那个本来就用来修复该团队的退役操作。三处写入上限都是拒绝而非截断：`TASK_TITLE_MAX`（200）、
`TASK_BODY_MAX`（2000）与 `TASK_LIMIT`（每个 Lead 200 条任务，含 `done`）。

## 2. 交接矩阵（P2-09）

成员承担的工作不只是它的 `assignment`。它还是这个 Lead 任务板上把该成员记为 `owner` 的那些未完成任务（`docs/roster-storage-zh.md` §1），而这些行在每个事件上如何变化，要在实现之前就定下来（AGENTS.md §4.8）。每个格子回答三个问题：

- 该成员的**未完成**任务如何变化；
- 调用**报告**了什么；
- 它的**已完成**任务是否移动。

**没有任何一个格子会移动 `done` 任务。** 已完成的工作属于完成它的那条记录，因此 `done` 行在表中每个事件上都保持 owner 不变，包括让它退役的那些事件。整个矩阵就建立在这一条规则上：交接交出去的是**尚未偿清的工作**，不是一份历史。

| 事件 | 成员的未完成任务 | 结果字段 | 已完成任务 |
|---|---|---|---|
| `spawn_member` 带 `replace` 成功，前任退役 | 在写墓碑之前改为归继任者所有：同样的行，新的 `owner` | `transferred`（数量）与 `transferred_tasks`（id）；退役记录不会给出第二份 | 留在前任的墓碑上 |
| 对**已退役**前任执行 `spawn_member` 带 `replace` | 改为归继任者所有，并连同其他所有无主的未完成任务：这些工作是被更早那次退役留下的，而这次替换正是它在等的继任者 | `transferred` 与 `transferred_tasks`，消息里会点名；退役这一半回答 `already-retired`，不再加字段 | 原地不动 |
| **继任者启动失败** | 什么都不动：前任原封不动且仍然活着 | 抛出的错误说明前任**没有**被退役，也不出现任何任务字段，因为没有任何任务移动 | 不变 |
| **继任者已启动、退役失败** | 已经移动过：交接是第一次写入，因此调用方启动的继任者仍然带着它的工作 | `predecessor_retired: false`；`transferred` **缺席**，因为这次调用没有转移任何东西（是上一次尝试转的） | 不变 |
| `retire_member` **没有继任者** | 清掉 owner：行仍是 `open` 并变为无主，因为工作依然欠着 | `unowned`（数量）、`unowned_tasks`（id），消息说明没有人会接手它们 | 留在墓碑上 |
| **恢复**一位任务已被转交的成员 | 不变：恢复恢复的是一条生命周期记录与一份产物，它不重新分配工作 | `unowned` / `unowned_tasks` 报告仍在等待认领的工作——这是事实，不是主张；不写入任何 owner | 不变 |
| 由**一次性清扫**执行的退役 | 清掉 owner，走的是模型本来也会调用的同一套退役流程——而只有清扫查看时它一无所有的成员才会被清，因为持有的 `open` 行就是阻止清扫的否决（`docs/member-lifecycle-zh.md` §2） | 触发调用的 `swept`/`swept_targets`；只有当某一行是在否决读取与退役之间才创建出来时，才会出现 `unowned`/`unowned_tasks` | 留在墓碑上 |
| 一条未完成任务，其 **owner 名字后来被新一代复用** | 按名字什么都不会发生：`owner` 是 **target**，而一个名字的第 2 代是 `reviewer-g2`，是另一个 target。新一代不会仅凭名字继承任何东西，而旧 target 仍可作为重新指派的有效 owner 句柄 | 无 | 不变 |
| 一条带 **`body`** 的任务穿过一次交接 | 和别的行一样被重新指派：正文随行移动，因为正文属于任务，而不属于碰巧持有它的成员 | 同样是 `transferred` / `transferred_tasks`；交接书只点 id 与标题，因此继任者用 `list_my_tasks` 从任务板上读正文（`docs/architecture-zh.md` §5.2） | 留在前任的墓碑上 |
| 一次**与交接相撞的工作板写入**（在交接落地之前就已算出的 `update`、`release` 或 `delete`） | `update` 只把它点名的字段应用到已存行上，因此改状态或改正文会保留继任者的 owner；`release` 与 `delete` 发现的这一行，其 `status`/`owner` 已不是它们读到的值，于是什么都不写 | `changed: false`，连同已存的那一行，以及说明什么变了、如何重做这次调用的消息；`delete` 也不会给出 `deleted` | 不变 |

这些格子依赖的前提：

- **交接是替换的第一次写入，早于墓碑。** 先成功启动，再用一次改动重新指派这些行，然后才写退役记录。因此启动失败不会移动任何东西，而墓碑写入失败留下的是“活着的成员，其工作已归继任者”——一种部分完成的生命周期，它的下一步是再调一次 `retire_member`，而不是丢掉一个任务。这个顺序与退役自身“先立碑”的规则（`docs/member-lifecycle-zh.md` §3）相反，理由相同：会失败的那一步，必须失败在可恢复的那一半上。
- **只有替换会收养无主工作。** 退役产生无主行，替换消费它们，因此带 `replace` 的 `spawn_member` 会接手所有无主的未完成行，包括并非它造成的那部分。别的操作都不认领它们，任何读取都不会写入 owner。
- **交接只写所有权，绝不写状态。** 行在交接过程中保持 `open`；只有 `task_board` 的 `action: update` 才会把它变成 `done`，这也是让它不再被继承的唯一途径。
- **工作板写入基于它落地的那一行重建，而“减去”有前提。** 每个按 id 定位的任务操作都会在串行化的改动内部重读该行（`docs/roster-storage-zh.md` §1）：`update` 合并它点名的字段，而 `release`/`delete` 在调用读取之后这一行被交接改动过时，会回答 `changed: false`，而不是清掉一个 owner 或删掉一行。这正是让上表中替换那一行在两次调用重叠而不仅仅是先后发生时依然成立的东西（ADR 0020）。
- **同一模型轮次里的两个工具。** 每次任务改动都是花名册表上的一次原子 `update`，与成员改动一样（`docs/roster-storage-zh.md` §1），因此同一轮次里的 `task_board` 调用与替换会看到彼此的写入，而不是互相覆盖。
- **由定义启动的继任者不可能是一次性的，因为文件不能声明生存期。** 如果继任者确实是扇出工作，`replace` 就在调用上写 `lifetime: "one-shot"`；此时与任何一次性成员一样适用同一道否决：这张矩阵刚刚交给它的工作会让它留在花名册上，直到 Lead 关闭那些行（`docs/member-lifecycle-zh.md` §2、`docs/architecture-zh.md` §6.1、ADR 0026）。

## 3. 工作板写入基于已存的那一行

**工作板的写入基于已存的那一行，并且在串行化的改动内部构建。** `task_board` 调用开始时的那次读取只陈述
**前提**，永远不是要写回的行：改动会在 `updateRoster` 交给它的记录里重新查找该任务，并从那一行构建下一行。
因此 `update` 只应用调用点名的字段——改状态会保留交接给该行的 owner，改正文会保留其余一切——而 `release`
与 `delete` 的效果是“减去”，于是它们只作用于调用读到的那个状态：当已存行的 `status`/`owner` 不再是快照里的
值时，它们什么都不写，并带着找到的那一行回答 `changed: false`。若这一行在读取与写入之间消失了，得到的拒绝
与未知 id 完全相同。这正是让“只有人换，工作不换”在并发下而不只是在顺序执行下成立的东西：替换写下的交接不会
被紧接着的工作板调用抹掉，而模型不需要跟踪任何 revision，schema 也不增加任何参数（ADR 0017 第 5 点、
ADR 0020）。
