# 交接书

> Owner: @FrozenYty · Revisit when: 交接书的形状、占位符或模板来源发生变化时

继任者在替换成员时收到什么，以及交接书模板可能来自的三个来源——团队文件、已存模板、内置形状——它们之间的优先级，以及文件存在时施加的写入拒绝。合成这份交接书的替换协议见 `docs/member-lifecycle-zh.md` §3；存放它的记录字段见 `docs/roster-storage-zh.md` §1。相关决策：ADR 0009、ADR 0015、ADR 0019、ADR 0021。

## 1. 继任者收到的交接书

替换会依据前任的记录与任务板合成继任者的交接书（`docs/member-lifecycle-zh.md` §3）；本节说明这份交接书携带什么、边界在哪里。

**交接书的形状有三个来源，顺序是：团队文件、已存模板、内置形状。** 反复替换成员的 Lead 可以把 `team/team.md` 随项目一起提交，也可以用 `handoff_template`（`docs/architecture-zh.md` §5）存一份模板，或者什么都不存而得到内置形状。文件只要存在就胜出，因此工具在每次读取时报告 `source`，并在文件存在时用文件路径拒绝写入或清除（`docs/handoff-zh.md` §2）。占位符是 `{successor}` 与 `{predecessor}`（两个 target）、`{label}`（前任的职责）、`{assignment}`（记录在案的职责）与 `{task_board}`（指向该 Lead 自有任务板的指针）。`{assignment}` 是必须的：省掉它，继任者只拿到前任的角色与任务板指针，却不知道继承了什么工作——而这正是交接的意义。模板在写入时或文件解析时校验：未知占位符会被按名字拒绝，因此拼写错误不会以字面文本的形式进入子代理。继任者自己的任务始终追加在渲染结果之后，任何模板都无法把它丢掉。渲染出的这一段上限 2000 个字符，超过就拒绝而不是截断；上限只在确有模板生效时才量，这正是“既没有文件也没有模板的 profile 与 P4-02 之前逐字节相同”的原因。已存模板属于某个 Lead 的花名册记录，因此两个 Lead 不会共用一份；团队文件属于项目，因此同一个项目里的两个 Lead 会共用它——这是刻意的。`list_members` 的行两者都不带。

**任务板随交接书一起过去，并且有上限。** 交接书不是工作区快照：一个从 200 行长清单起步的成员，比只拿到五个 id 的成员更糟。因此合成会追加**一行**，按 id **和**标题点出前任的未完成任务——只给其中一样都不好用：继任者查不到的 id 要多一次往返，而只有标题又没法把任务标成完成——并且这一行有两重上限：最多 5 行、最多 600 个字符，后者相当于五条满长标题（`TASK_TITLE_MAX`，200）再加 id 的余量。**这一行只带 id 与标题，绝不含某一行的 `body`**：正文的上限是为任务板定的（`TASK_BODY_MAX`，2000），不是为子代理的提示词定的，每行一条满长正文就会撑破 600 字符这条界线——继任者用 `list_my_tasks` 读正文（Lead 用 `task_board`），也就是指针句本来就把它指向的那块板（ADR 0020、ADR 0022）。任何一重上限过不去，整行就被丢掉，继任者仍拿到 `{task_board}` 指针句，也就是 P2-09 之前那个版本给出的交接书。因此当前任没有任何未完成任务时，交接书与旧版逐字节相同，并有测试钉住这一串——只有确实在途的工作才会以 id 与标题进入交接书，而且永远不含 `done` 行。

**模板保有自己的那一行。** 继承任务这一行追加在渲染结果之后、继任者自己的任务之前，因此模板既丢不掉它也重复不了它，而 `{task_board}` 占位符的含义和以前完全一样：指针。模板并不要求提到任务板——会提到的是默认形状。

**尚未实现、因此不作为行为描述。** 没有“成员自己写交接书”这回事，也没有交接书文件：向成员索要交接书要花一次模型往返，而需要交接时它往往正好无响应或已失败，所以交接书由记录与任务板合成。代码里也没有任何“用工作区核对职责或任务”的步骤——那是 Lead 的判断，插件只负责点出它存下的那些行。

## 2. 团队文件（v0.19.0）

成员作用域在 v0.16.0 搬到了磁盘上；团队作用域也想为那个塑造交接的设置做同样的事。交接书模板曾是唯一没有 diff、没有评审、也无法在同一个项目里的两个 Lead 之间共享的团队设置，所以它现在是一个随项目提交的文件：`<Lead 工作目录>/team/team.md`，走与成员定义相同的 `workingDirectory` 服务（`docs/architecture-zh.md` §6）。它刻意**不属于**定义查找链：定义从 `.agents/team/definitions`、再 `team/`、再随包模板读取，而团队文件只有一个家，也没有随包对应物（ADR 0021、ADR 0029）。文件正文就是交接书模板，通过已存模板所过的同一套 `handoffTemplateProblem` 规则校验。

**文件名被保留，这就是对扫描冲突的回答。** `team.md` 会被成员定义扫描跳过，因此它永远不会被误认成成员定义——`team.md` 不声明 `name`，否则每次 spawn 都会把它报成一个坏定义。成员仍然可以在别的文件里声明 `name: team`：文件名不是身份（ADR 0018），保留的是这一个路径，不是一个名字。

**frontmatter 目前为空。** 它由同一套已记录的子集解析，可接受字段为零，因此没人要求的团队设置会连行号一起按名字拒绝，而不是被悄悄带上。将来的团队设置是往这个集合里加一个字段，不是再写一个解析器。

**生效模板有三个来源，按此顺序。**

| 来源 | 何时生效 | 合成做什么 |
|---|---|---|
| `file` | `team/team.md` 存在且解析出可用模板 | 渲染文件正文；已存模板被遮蔽 |
| `stored` | 没有可用文件，且该 Lead 的 `handoffTemplate` 通过内容规则 | 渲染已存模板，行为与 v0.11.0 相同 |
| `builtin` | 既没有可用文件，也没有可用的已存模板 | 渲染内置形状，与从未有过两者的 profile 逐字节相同 |

`handoff_template` 的读取形式会报告 `source`、生效的 `template`、文件存在时的路径、文件不可用时的 `file_problem`，以及已存值自己的 `stored`/`valid`/`problem`。文件存在但未通过校验——未知占位符、缺少 `{assignment}`、模板超长、未知 frontmatter 字段、读不出来或超过大小上限——会被报告，且永远不会成为生效模板；接下来是已存模板，最后是内置形状。这与“已存值不再通过校验”的退路完全相同，也正是它阻止文件里的拼写错误以字面文本进入子代理。

**文件存在时，写入存储会被拒绝。** 文件胜出，因此接受写入就成了静默无操作：模型会以为自己改变了交接书，而文件仍在合成每一个继任者。保存与清除给出同一条拒绝，并且点名文件与要做的编辑：

```
handoff_template: the team file "<绝对路径>/team/team.md" is in effect, so a stored template would be
shadowed and this write would change nothing. Edit that file to change the brief, or remove it to use
handoff_template again.
```

**哪些东西仍留在运行时记录里，为什么。** **任务**不搬到文件里。任务是生命周期状态，与墓碑在同一次写入里落盘，并随替换移动（ADR 0017）：它属于 Lead 的这次运行，不属于项目的源码树。模板是相反的一类状态——一种形状偏好，对团队成立，而不是对某个成员或某次运行成立——这正是提交进仓库的文件擅长的事。划分是按种类，不是按新旧：文件放的是同一个项目里两个 Lead 应当共享的东西，记录放的是只有这次运行知道的东西。因此共享一个 `team/` 目录对模板是特性，对工作板则会是缺陷。

## 3. 记录里存下的模板

`handoffTemplate` 是这条记录上唯一描述 Lead 而不是成员的字段。它的**类型**在加载时校验，而它的
**内容**——占位符词表、必须引用 `{assignment}`、长度上限——在写入时校验，并由读取形式重新报告（`docs/architecture-zh.md` §5）。
这个分工是刻意的：存储设施在打开域时会校验每个 Lead 的每条记录，因此为某个 Lead 的一处交接书偏好而拒绝
整个花名册，会把所有团队都藏起来。存储的模板一旦不再通过校验，会被报告而不是被悄悄丢掉，而合成会退回
内置交接书，而不是把出错的 token 写进子代理的提示词。从 v0.19.0 起，文件正文在解析处就过同一套内容
校验，未通过的文件不会成为生效模板（§2）。
